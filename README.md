# G3M Controller

Windows 端漫步者 / HECATE G3M Pro 鼠标配置工具。常驻托盘占 **7 MB** 内存，按需打开设置窗口改配置。

不需要安装 HECATE Connect，不需要管理员权限，不依赖专用驱动。

---

## 它做什么

| 功能 | 状态 |
|---|---|
| 读取设备全部状态（设备头、板载配置、按键映射、电量） | ✅ 真机验证 |
| **修改 7 个 DPI 档位**（数值 / 启用开关 / 灯光颜色） | ✅ 真机验证 |
| **切换当前 DPI 档位** | ✅ 真机验证 |
| **修改回报率** 125 / 250 / 500 / 1000 / 2000 Hz | ✅ 真机验证 |
| **修改直线修正、波纹修正、按键防抖、静默高度** | ✅ 真机验证 |
| 托盘显示电量、充电状态、低电量提醒、开机自启 | ✅ |
| 电量历史（8 天采样、24 小时 / 7 天曲线、续航估算） | ✅ |
| 界面背景可切换云母 / 亚克力 / 普通灰色 | ✅ |
| 按键映射**写入** | ❌ 见下方说明 |

所有写入操作都会：**写入前自动备份** → 写入 → **重新读取并逐字节比对** → 不一致就报错。
备份在 `%LOCALAPPDATA%\G3M Controller\Backups\`，最多保留 30 份，可在「高级」页一键还原。

## 按键映射为什么只能读不能写

读取完全可用，能准确显示 6 个物理键的当前分配。写入在这台设备的固件上走不通，实测结论：

| 尝试的通道 | 结果 |
|---|---|
| `0x0B`（易失写入，原 macOS 项目使用） | 固件直接拒绝，返回命令错误 |
| `0x09`（持久写入，原 macOS 项目声称可用） | 设备接受，响应格式与真正生效的 `0x06` 完全一致，但映射表内容毫无变化 |
| `0x08`（按 `0x05 读 / 0x06 写` 的配对规律推测） | 同样被接受，同样无效 |
| `0x09` + 同会话追加 `0x06` 配置写入 | 无效 |

对照实验排除了误判：**已知可用的配置写入命令 `0x06` 同样会回显旧数据**，所以"回显"本身不能说明一条命令是读还是写。`0x08` 与 `0x09` 表现得像真正的写命令，只是对映射表不起作用。

参考项目 `g3mpro-macos` 的 README 把「退出映射恢复」列为**真机发布前仍需检查**的项目，该路径很可能并未在实际设备上验证过。

因此界面目前只提供读取。`G3mController.WriteKeyMapping` 的代码保留着（在别的固件版本上可能可用），但调用方必须处理 `VerifyFailed`。

## 界面设置

设置程序导航栏底部有「设置」页，可以调主题与背景材质，选择立即生效并写入
`%LOCALAPPDATA%\G3M Controller\settings.json`。

**主题**（默认跟随系统）

| 选项 | 说明 |
|---|---|
| 跟随系统 | 由 Windows 的浅色/深色设置决定，系统变化时窗口与标题栏一起切换 |
| 浅色 | 始终浅色 |
| 深色 | 始终深色 |

**背景材质**（默认云母）

| 选项 | 说明 |
|---|---|
| 云母 | 跟随桌面壁纸取色，窗口失焦时保持材质 |
| 亚克力 | 模糊更强、带噪点，能透出窗口后面的内容 |
| 普通灰色 | 系统主题背景色，不透明，兼容性最好 |

### 三个实现要点

- **标题栏是自绘的**（内容延伸进标题栏）。系统画的标题栏既不跟随应用主题，也会在云母背景上
  留一条突兀的色带。自绘之后材质能直接透上来，按钮颜色也能精确跟随深浅色。
- **切换主题后必须重建背景材质**。云母与亚克力的深浅变体在实例创建时就确定了，
  沿用旧实例的话浅色主题下背景会仍是深色，跟内容对不上。
- **「跟随系统」要真的跟随**。窗口内容的主题由 `RequestedTheme` 自动传播，
  但标题栏按钮是系统按我们给的颜色画的，不会自己变，因此订阅了系统配色变化事件
  并重新上色（回调在线程池线程上触发，需要切回 UI 线程）。

另外两条容易踩的：

- **系统不支持的材质会被置灰**，而不是让用户选了之后没反应。若存档里的选择在当前系统上不可用，
  启动时会静默退回普通灰色，并把退回原因显示在设置页——设置页显示的是**实际生效**的材质，
  不是存档里的期望值，避免出现"看起来选中了但没生效"的假象。
- **半透明材质要求窗口内容不画不透明背景**，否则材质会被整块盖住；反过来选"普通灰色"时必须
  补上实底，否则窗口会变成全透明。`NavigationView` 默认会自己画一层不透明背景，
  内容区、导航栏、边框四层背景都要显式改成透明。

## 架构

两个进程，一个共享协议库。**"低占用"只针对常驻的托盘进程。**

```
G3M.Tray.exe      WinForms，常驻托盘     实测专用工作集 7 MB
G3M.Settings.exe  WinUI 3，按需打开      关掉即退
G3M.Core.dll      共享协议库
```

两个进程各自独立打开同一个 HID 设备，**不需要 IPC**。设备以
`FILE_SHARE_READ | FILE_SHARE_WRITE` 打开，已实测两个句柄可以并发事务，
甚至一个句柄处于配置会话（`0x01`…`0x02`）中时另一个句柄仍能正常轮询电量。

历史文件只由托盘进程写入，设置进程只读——单写者让文件不需要跨进程锁。

```
src/G3M.Core/          HID 层、协议、模型、历史、备份
src/G3M.Tray/          托盘宿主（绝不创建 Form）
src/G3M.Settings/      WinUI 3 设置程序
tools/G3M.Probe/       命令行诊断工具
```

---

## 协议要点

64 字节报文：`[0]=0x04`，`[1..2]=小端16位校验和`（`[3..63]` 之和），
`[3]=命令`，`[4]=长度`，`[5..6]=小端16位偏移`，`[8..]=载荷`。

配置读写必须包在 `0x01`（开会话）/ `0x02`（结束，**前摇 10 ms**）之间；
批量读写按 `header[6]` 分块（本机为 24 字节）。

| 命令 | 用途 |
|---|---|
| `0x01` / `0x02` | 开始 / 结束配置会话 |
| `0x03` | 读 34 字节设备头 |
| `0x05` / `0x06` | 读 / 写 84 字节板载配置（偏移 = 86 × 配置编号） |
| `0x07` | 读按键映射表（槽位数 × 3 字节） |
| `0x1A` 子命令 `0x06` | 查电量 |
| `0x28` / `0x29` | 切换 DPI 档位 / 设置回报率 |
| `0xAA` | 在线探测 |

本机实测：厂商集合 `usage_page=0xFF1C usage=0x0092`，收发各 64 字节，无 Report ID 前缀；
传感器 13205，DPI 步进 50、基准 50、7 档；按键槽位 42 个；板载只有 1 个有效配置档案。

按键 3 字节编码：`10 xx yy` = 鼠标按键（byte1 为按键位），`13 03 00` = DPI 循环，
`20 mm kk` = 键盘报文（byte1 为修饰键掩码，byte2 为 HID 键码）。

## 构建

需要 .NET SDK 10：

```bash
winget install Microsoft.DotNet.SDK.10
```

```bash
dotnet build G3MController.slnx -c Release

# 托盘：框架依赖，328 KB
dotnet publish src/G3M.Tray -c Release -r win-x64 --self-contained false -o dist/G3M.Tray

# 设置程序：自包含，88 MB
dotnet publish src/G3M.Settings -c Release -o dist/G3M.Settings
```

### 两个已解决的坑

**1. 设置程序必须自包含。** 本机 Windows App Runtime 的框架包是 `8000.946.1701.0`，
但注册的 DDLM 最高只到 `8000.921.1539.0`。非打包 WinUI 3 应用要求两者严格一致，
缺失就**静默退出**——没有报错、没有事件日志。装官方运行时安装器也补不上 946 版 DDLM。
`WindowsAppSDKSelfContained=true` 完全绕开这个机制。

**2. 不要引用 `Microsoft.WindowsAppSDK` 元包。** 它会把整个 Windows AI 栈拖进来
（`onnxruntime.dll` 21 MB + `DirectML.dll` 18 MB + WebView2 + Widgets），
鼠标工具一行都用不到。只引用 `.Base` / `.Foundation` / `.WinUI` 三个细粒度包，139 MB → 88 MB。

另外：`G3M.Core` 与 `G3M.Tray` 刻意使用不带平台版本号的 `net10.0-windows`，
因为带版本号的 TFM 会通过 `Microsoft.Windows.SDK.NET.Ref` 拉进 24 MB 的 WinRT 投影程序集。
只有 WinUI 项目需要 `net10.0-windows10.0.19041.0`。

## 诊断工具

```bash
cd tools/G3M.Probe

dotnet run -- snapshot          # 打印设备头、配置、按键映射、电量
dotnet run -- battery           # 只读一次电量
dotnet run -- write-identity    # 把当前配置原样写回，验证写入+校验链路
dotnet run -- set-dpi 0 1700    # 改第 1 档 DPI
dotnet run -- keymap            # 只打印按键映射表
dotnet run -- restore           # 用最近一次备份整体还原
```

界面行为异常时先用它对照，可以快速判断问题出在协议层还是界面层。

## 已知限制

- 按键映射只能读，原因见上
- 板载只有一个有效配置档案，不支持多档案切换
- 续航估算基于本程序运行时记录的数据，程序没运行的时段无法补全
- 估算要求最近至少 30 分钟连续放电数据且电量下降 2% 以上，否则显示"暂无"而不是给猜测值
- 修改左键 / 右键等关键按键的防护逻辑已实现，但因写入不可用而未启用
